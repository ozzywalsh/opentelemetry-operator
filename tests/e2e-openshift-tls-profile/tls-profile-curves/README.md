# Cluster TLS Profile Curve Propagation

This test verifies that the groups (elliptic curves) of the cluster-wide TLS
security profile reach both generated ConfigMaps: the collector's, as
`curve_preferences`, and the Target Allocator's, as part of the `https` block.

## Test Overview

1. Save the cluster's APIServer TLS security profile and replace it with a
   `Custom` profile that names an explicit `groups` list.
2. Deploy a collector with a TLS-enabled OTLP gRPC receiver and a Target
   Allocator with mTLS enabled.
3. Check the generated collector ConfigMap for the translated
   `curve_preferences`, and the Target Allocator ConfigMap for `min_version`,
   `cipher_suites` and `curve_preferences` under `https`.
4. Flip the profile to a second `Custom` profile that differs only in its
   `groups` list, and check that the graceful restart regenerates both
   ConfigMaps with the new curves.
5. Restore the original APIServer profile.

## Prerequisites

- OpenShift cluster with the `TLSGroupPreferences` feature gate enabled. When
  the gate is off, the API server prunes `spec.tlsSecurityProfile.custom.groups`
  and the test skips itself with a message rather than failing.
- OpenTelemetry Operator installed with `--tls-cluster-profile` and
  `--tls-configure-operands`
- `oc`, `kubectl`, `yq`, `jq` and `openssl`
- Cluster admin permissions (the test patches the cluster-wide APIServer resource)

cert-manager is **not** required: the Target Allocator mTLS certificates are
generated by the test and passed in through `useCertManager: false`.

## Vocabularies

The three configuration surfaces spell the same group differently. The operator
translates explicitly.

| OpenShift `groups` | Collector `curve_preferences` | Target Allocator `https.curve_preferences` |
|---|---|---|
| `X25519` | `X25519` | `29` |
| `secp256r1` | `P256` | `23` |
| `secp384r1` | `P384` | `24` |
| `secp521r1` | `P521` | `25` |
| `X25519MLKEM768` | `X25519MLKEM768` | `4588` |

The Target Allocator uses the IANA numeric group IDs from the TLS Supported
Groups registry.

The test uses only groups that the collector's `configtls` allowlist accepts.
`SecP256r1MLKEM768` and `SecP384r1MLKEM1024` have no collector spelling, and
naming either makes collector pods fail to start with `invalid curve type`.

## Test Steps

### Step 0: Certificates and cluster profile
- **Scripts:** [`00-create-certs.sh`](00-create-certs.sh), [`00-patch-profile.sh`](00-patch-profile.sh)
- Create a CA, a Target Allocator server certificate, a collector client
  certificate, and a server certificate for the OTLP gRPC receiver
- Save the current APIServer TLS profile in the `tls-curves-backup` ConfigMap
- Decide through a server-side dry run whether the cluster accepts `groups`
- Patch the APIServer to profile A: `VersionTLS12`, GCM ciphers, groups
  `X25519MLKEM768`, `X25519`, `secp256r1`, `secp384r1`

### Step 1: Deploy the collector and Target Allocator
- **Script:** [`01-wait-for-operator.sh`](01-wait-for-operator.sh), **manifest:** [`01-install.yaml`](01-install.yaml)
- Wait for the restart the profile change triggers, and for the webhook endpoint
- Apply the collector and assert that the collector StatefulSet and the Target
  Allocator Deployment are ready

### Step 2: Verify profile A
- **Script:** [`verify-curves.sh`](verify-curves.sh)
- Collector ConfigMap: `min_version: "1.2"`, non-empty `cipher_suites`, and
  `curve_preferences: ["X25519MLKEM768","X25519","P256","P384"]`
- Target Allocator ConfigMap: `https.enabled: true`,
  `https.min_version: VersionTLS12`, non-empty `https.cipher_suites`, and
  `https.curve_preferences: [4588,29,23,24]`

### Step 3: Flip the profile
- **Script:** [`03-flip-profile.sh`](03-flip-profile.sh)
- Patch the APIServer to profile B: the same minimum version and ciphers, groups
  `X25519` and `secp521r1`. Only the groups change, so the groups change alone
  has to trigger the graceful restart.
- Poll both ConfigMaps for the new curves, then wait for the rollouts

### Step 4: Verify profile B
- **Script:** [`verify-curves.sh`](verify-curves.sh)
- Collector ConfigMap: `curve_preferences: ["X25519","P521"]`
- Target Allocator ConfigMap: `https.curve_preferences: [29,25]`

### Step 5: Restore
- **Script:** [`restore-apiserver.sh`](restore-apiserver.sh)
- Re-apply the saved profile, or remove the field when none was set

## Running the Test

```bash
chainsaw test tests/e2e-openshift-tls-profile/tls-profile-curves
```

## Manual Cleanup

```bash
kubectl delete namespace chainsaw-otel-tls-profile-curves --ignore-not-found
oc patch apiserver cluster --type json \
  -p '[{"op":"remove","path":"/spec/tlsSecurityProfile"}]' 2>/dev/null || true
```

## Important Notes

- The test **patches the cluster-wide APIServer TLS profile**. It runs with
  `concurrent: false` and a top-level catch handler that restores the profile on
  any failure.
